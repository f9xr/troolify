API Key Hasher: Store Credentials Without Storing the Secret

If your database stores API keys in plain text, a single read-only leak exposes every integration. This API key hasher shows how to convert a key into a digest you can store safely, using SHA-256, SHA-512 or PBKDF2 with a salt, and produces the Node.js code to verify a presented key against it.

Fast hash or key-derivation?

API keys are high-entropy random strings, so a single fast SHA-256 digest is usually enough: an attacker who steals the digest cannot feasibly reverse a long random key. PBKDF2 stretches a low-entropy secret and is the safer choice when the stored value is a human password rather than a machine key. The tool lets you pick with that trade-off in mind.

Why salting and constant-time comparison matter

A unique salt per key defeats precomputed lookup tables, and a constant-time comparison avoids leaking the correct prefix through timing. The generated snippet uses timingSafeEqual for exactly that reason.

How to use API Key Hasher

  1. Paste the API key you want to store.
  2. Choose SHA-256, SHA-512 or PBKDF2 and, for PBKDF2, an iteration count.
  3. Copy the hex or Base64 digest into your database column.
  4. Drop the Node.js snippet into your verification path.

Tips for getting accurate results

  • Generate a fresh salt per key when using PBKDF2 and store it alongside the hash.
  • Use a constant-time comparison, never a plain string equality, for the digest.
  • Keep the digest column long enough to avoid truncation surprises.

Key takeaways

  • Storing a hash instead of the key limits the blast radius of a leak.
  • High-entropy keys suit a fast digest; passwords suit PBKDF2.
  • Salting and constant-time comparison round out a safe implementation.

Frequently asked questions

Should I hash API keys or encrypt them?

Hash them when you only ever need to verify. Encrypt only if you must recover the original key, which is rare and risky.

How many PBKDF2 iterations?

Aim for a value that keeps verification under a few hundred milliseconds on your hardware; 210,000 is a reasonable SHA-256 baseline.

Do I need a salt for SHA-256 keys?

For long random keys it is optional, but a salt is cheap and harmless, so include one.

Is my key sent anywhere?

No. Hashing happens in your browser with the Web Crypto API.

Why timing-safe comparison?

It prevents an attacker from learning the correct hash one byte at a time from response timing differences.

Conclusion

Treat API keys like passwords: store the digest, not the secret. This API key hasher gives you the hash and the code to verify it. Hash other values with our SHA hash generator.
